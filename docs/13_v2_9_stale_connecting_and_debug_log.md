# 13. v2.9：车旁“第一次太远失败后不再连接”的修复与持久日志

本文档记录 2026-11-05 09:45 左右的事故分析：

- 锁屏摇一摇、电源键三连都触发了震动（说明手势识别正常）。
- 但车辆没有解锁。
- 打开银河 App 后发现蓝牙钥匙未连接。

## 一、为什么当时的日志看不到

v2.9 之前日志只写到：

- in-app 80 行环形缓冲；
- `logcat`（`adb logcat -s GeelyKeyRadar`）。

事故发生在 09:45，10:17 拉取时 logcat 中 `GeelyKeyRadar` 已从 10:10 才开始（进程/缓冲区已滚动），09:45 的记录不存在，无法直接还原。**这是本次新增持久日志的直接原因。**

## 二、根因推断（与代码路径完全吻合）

v2.8.1 的 `performManualControl()` 有两个互相叠加的问题：

1. **“连接中”状态可能是陈旧的**
   - 第一次在较远处触发时，`checkAndAutoWakeGeelyOnApproach()` 在 `-95 dBm` 就唤醒银河；距离太远，V2 鉴权失败。
   - Geely 回调可能留下 `lastBleStatus=1`（正在连接）或 `getBleConnectStatus()==1`。
   - 后续在车旁再摇/三连时，代码把它当成“银河正在连接”，只等待、**不重新唤醒**。
   - 超时逻辑又在 `bleStatus==1` 时不断延长 12s，或（无近期广播时）6s 直接放弃，表现为“车旁怎么都不连”。

2. **没有近期广播时直接放弃**
   - v2.8.1 如果 90s 内没扫到车辆广播，且不是 status=1，会直接语音“未发现车辆”并返回，**不尝试唤醒**。
   - 息屏扫描被 OEM 降频时，车就在旁边也可能暂时没广播，于是手动操作被误判为“车不在附近”。

用户描述的“第一次太远连不上，后续直接放弃”与上述路径一致：第一次失败留下 stale connecting，后续每次都在等待/提前放弃，没有发起新的连接。

## 三、v2.9 修复

### 1. 只信任“新鲜”的 status=1

```text
freshConnecting = status==1 && (now - lastBleStatusChangedMs) < 8000ms
```

- 银河真实连接窗口约 5s；8s 内视为真正在连接，只等待、不重复唤醒。
- 超过 8s 仍 status=1 → 判定为陈旧/失败，**强制重新唤醒**。
- `lastBleStatusChangedMs` 在 `onVehicleBleStateChanged()` 和绑定状态变化时更新。

### 2. 手动操作永远至少尝试一次

- 不再因为“90s 内没广播”直接返回。
- 即使 `carSeen=false`，摇一摇/电源键/手动按钮也会调用一次 `wakeAndConnectGeelyBle()`。
- 日志明确写：`（90s 内无广播，仍强制尝试一次）`。

### 3. 超时后强制重连，而不是无限延长

```text
status=1 新鲜：再等 6s
仍未连接：
  carSeen=true  → 最多 2 次强制重连，每次 10s
  carSeen=false → 最多 1 次强制重连，每次 7s
仍失败 → 语音“未发现车辆，蓝牙连接失败”
```

- 不再出现 `bleStatus==1` 无限延长 12s 的死循环。
- 每次重连都重新调用 `wakeAndConnectGeelyBle()`，而不是只等 Geely 自己恢复。

### 4. 自动唤醒也让路

- `checkAndAutoWakeGeelyOnApproach()` 和亮屏预连接只在 `isGeelyFreshlyConnecting()` 为 true 时跳过；陈旧 status=1 不再阻止自动唤醒。

## 八、电源键三连的识别机制与 2s 窗口 Bug

### 1. 原理

Android **没有给第三方 App 直接拦截电源键的 KeyEvent**。我们的方案是监听屏幕状态广播：

```text
ACTION_SCREEN_OFF / ACTION_SCREEN_ON
2s（v2.9.1 起 3s）内出现 3 次状态变化 → 视为电源键连按三次
```

无论从亮屏开始（灭-亮-灭）还是息屏开始（亮-灭-亮），都会产生 3 次切换。

### 2. 实测发现的 Bug

v2.9.0 及以前窗口是 **2000ms**。v2.9.1 加了逐次日志后，一次真实三连：

```text
[10:24:28.247] 🔋 电源键状态变化 1/3，窗口 3000ms
[10:24:28.893] 🔋 电源键状态变化 2/3 (+645ms)，窗口 3000ms
[10:24:30.288] 🔋 电源键状态变化 3/3 (+1395ms)，窗口 3000ms
[10:24:30.288] ✅ 电源键三连识别成功
```

第一次到第三次总跨度 **2041ms**，刚好超过旧的 2000ms 窗口 → 旧版会漏掉。用户按得快时能触发，按得稍慢（自然节奏）就“没反应”，与“有时候灵敏、有时候没反应”完全吻合。

### 3. v2.9.1 修复

- 窗口 **2000ms → 3000ms**，覆盖自然的三连按节奏。
- 冷却 **3000ms → 2000ms**；冷却中会清空计数，不再留下陈旧 3 次在冷却后误触发。
- 每次屏幕状态变化都写日志：`电源键状态变化 N/3 (+间隔ms)`；能直接看出是“事件没来”还是“窗口超时”。
- 电源键三连的震动改为**固定 1 秒**（`vibratePowerTripleDetected`），不再依赖锁屏/亮屏状态；旧版亮屏时是 55/70/55ms 双短震，很容易感觉“没反应”。
- 触发日志：`✅ 电源键三连识别成功` → `★ 电源键三连触发【解锁/上锁】`。

### 4. 仍然存在的边界

- 厂商对极快电源键做防抖，可能只上报 1~2 次屏幕状态；日志会显示只有 1/3、2/3，这不是窗口问题，而是系统没给事件。
- AOD/息屏显示下第一次按键可能只点亮 AOD、不产生 `ACTION_SCREEN_ON`，需要多按一次。
- 三次按键总跨度超过 3s 仍会漏；可以看日志调整窗口。
- 不 Root/不使用无障碍无法直接拦截电源键；这是目前最稳的非侵入方案。
