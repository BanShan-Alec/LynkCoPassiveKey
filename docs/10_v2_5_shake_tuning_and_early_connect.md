# 10. v2.5：双次摇一摇防误触、提前连接、关门后摇一摇上锁、开锁/闭锁独立开关

本文档记录 v2.5.x 针对实车测试四个问题的修复：

1. 摇一摇太容易误识别 → 改为「同轴左右/上下摇两次」才触发。
2. 到车旁约 10s 后摇动才生效 → 提前唤醒并建立吉利 V2 蓝牙连接。
3. 开车门再关门后，摇一摇无法锁车 → 手动/摇一摇使用窄口径行车门控，不再被 A2DP/PTReady 误拦。
4. 开锁/闭锁开关分开 → 自动解锁/自动上锁 + 摇一摇解锁/摇一摇上锁，共 4 个独立开关。

---

## 一、双次摇一摇检测（防误触）

### 1. 算法

`KeyRadarService.shakeListener` 改为基于**高通线性加速度**的方向性检测：

- 用低通估计重力：`g = 0.90*g + 0.10*acc`，线性加速度 `l = acc - g`。
- 单峰阈值：`|l| >= 20 m/s²`，峰间隔 ≥120ms。
- 取绝对值最大的轴作为主方向（x=左右，y=上下，z=屏幕法向），记录符号。
- 同一个主轴上：**4 个峰 + 至少 2 次方向反转 + 1800ms 窗口** 才算触发（即左右-左右或上下-上下两次完整摇动）。
- 触发后冷却 3s；不同轴的峰直接忽略，避免走路/翻转误触。

旧规则是「3 个峰 / 900ms / 16 m/s²」，且只看模长差，不区分方向，所以走路、放桌面、单手操作都可能触发。

### 2. 实测基线

用 App 内「🔬 记录摇一摇原始数据 15s」在桌面静置录制（手机未移动）：

```text
samples 663
p99 0.08 m/s², max 0.11 m/s²
peaks >= 10 / 15 / 20 / 25 / 30: 全部为 0
```

静态噪声只有 0.1 m/s² 量级，20 m/s² 的阈值有足够余量；误触主要来自旧算法缺少方向/次数约束，而不是阈值太低。

### 3. 数据记录与调参

手机端「🟢 手机侧」卡片底部新增：

```text
🔬 记录摇一摇原始数据 15s (锁屏后按左右/上下各摇两次，供分析)
```

点击后立即锁屏，在 45s 引导窗口/车辆附近摇动；15s 后写入：

```text
/sdcard/Android/data/com.luca.geelykeyradar/files/shake_diag_<yyyyMMdd_HHmmss>.csv
```

CSV 列：`timestamp_ms,x,y,z,lx,ly,lz,linear_mag`。可用 `adb pull` 拉取分析；如果实际摇动峰值低于 20 或峰数不足，可按数据下调阈值/峰数。

## 二、提前建立吉利蓝牙连接

旧逻辑：`checkAndAutoWakeGeelyOnApproach()` 只在 `rssi >= -90 dBm`（约 13m）才注入 ScanResult 唤醒银河，且 3.5s 才重试一次；用户走到门前才开始握手，V2 鉴权约 3.07s，于是「到车旁约 10s 后摇一摇才生效」。

v2.5 修改：

- 唤醒门槛放宽到 **`rssi >= -95 dBm`（约 18~20m）**。
- 重试节流动态化：`rssi >= -88` 时 **1.5s**，外缘 **2.5s**。
- **亮屏/解锁** 时若车辆最近出现过且银河未连接，立即 `wakeAndConnectGeelyBle("亮屏提前预连接")`。
- App 回到前台改为 `refreshVehicleStateNow()`（必要时唤醒连接），不再只发轻量查询。
- 仍然不主动 `connectGatt` 抢占车机唯一槽位；只注入 `ScanResult` 让银河自己建链，避免车机停止广播。

目标：用户在 15~20m 外被扫到时就开始鉴权，走到车门时连接已就绪，摇一摇/靠近解锁不再等 10s。

## 三、关车门后摇一摇无法锁车

### 根因

旧 `evaluateInCarOrDrivingState()` 把 **A2DP/HFP 车载音频连接** 和 **PTReady=1 / 发动机运行** 都视为「行驶中」，直接否决所有解闭锁。开车门后车机通电、音频/附件电源常保持连接，关门后短时间内仍是「车内音频连接」，于是摇一摇上锁被静默拦截。

### 修复

新增窄口径门控 `evaluateHardDrivingState()`，只拦截真正的运动：

- 银河通知栏状态为「行驶中」；
- GPS 车速 > 6.5 km/h；
- 刚停车且仍有残余速度（`now < drivingHoldUntilMs && speed > 0.5 m/s`）；
- 车辆 EPB 已释放且正在移动。

**不再**因为 A2DP/HFP 音频或单独的 PTReady/发动机状态而否决手动/摇一摇。

下发路径：

- `GeelyAidlBridge.sendManualFastControl()` → `sendFastControlInternal(..., manual=true)`。
- 初始检查和 5 阶重发都使用 `getManualDrivingBlockReason()`（窄口径）。
- 摇一摇与手动 RKE 按钮都走 manual 通道；自动靠近解锁/远离上锁仍走原来的全量安全门控（避免在车内自动锁车）。
- UI 手动按钮的禁用状态改用 `manualControlBlocked`（来自窄口径），关门后不会再显示「禁锁」并把按钮灰掉。

## 四、开锁/闭锁开关分开

现在共 **4 个独立开关**：

| 开关 | key | 控制 |
| :--- | :--- | :--- |
| 靠近自动解锁 | `auto_unlock` | RSSI ≥ 解锁阈值，满足一次即解锁（含 3 米缓冲反误锁重解） |
| 远离自动上锁 | `auto_lock` | RSSI ≤ 上锁阈值，连续满足驻留时长才锁车 |
| 摇一摇解锁 | `shake_unlock` | 摇一摇识别为解锁时是否执行 |
| 摇一摇上锁 | `shake_lock` | 摇一摇识别为上锁时是否执行 |

- 摇一摇先按当前/最后确认锁态判断目标动作，再检查对应的摇一摇开关；关闭的动作会写日志并直接返回，不会误发。
- 两个摇一摇开关都关闭时，加速度计不注册，省电。
- 自动开关与摇一摇开关互不影响；手动按钮始终可用（受窄口径行车门控约束）。

## 五、验证

- 设备：iQOO Neo10 Pro (`V2426A` / Android 16)，v2.5.1 安装无 crash，前台服务正常。
- UI 实测：4 个开关与「记录摇一摇原始数据 15s」按钮正常显示；当前阈值保持 `-78 / -83 / 3.2`。
- 摇一摇数据记录实测：15s 录制生成 663 个样本、42KB CSV，静态噪声 max 0.11 m/s²。
- 传感器：锁屏 `Asleep` 时 `dumpsys sensorservice` 可见 `lsm6dsve_acc` 50Hz 注册。
- 关门后锁车、提前连接、真实摇动手感需用户实车复测；如仍偏难/偏易，用记录按钮采集真实摇动 CSV 后再调 `SHAKE_DELTA_THRESHOLD_MS2` / 峰数。

## 六、已知边界

- 双次摇一摇要求 1.8s 内完成两次；如果用户习惯慢摇，可把窗口放宽或把峰数降到 3，但会牺牲防误触。
- 提前连接仍受 AOSP/OEM 息屏扫描降频影响；首帧广播越晚，提前量越少（WakeLock、扫描心跳已尽量补偿）。
- 窄口径门控在极低速挪车（<6.5km/h）且通知栏状态未更新时可能允许手动锁车；这是为了满足关门后立即锁车的取舍，车机自身仍会做安全校验。
