# 24. v3.14：P 档/人已下车仍显示“行驶中”导致无法锁车

## 一、根因

银河没有把“P 档”作为一个独立字段直接给我们；App 只能用这些信号推断：

- `0x0121` 的 EPB/eptReady/engine；
- 银河通知栏/小组件文字“行驶中/已驻车”；
- 手机 GPS 速度；
- 手机与车机的 A2DP/HFP 音频连接。

旧逻辑有三个误判：

### 1. A2DP/HFP 被当成“行驶中”

```java
if (a2dp == CONNECTED || headset == CONNECTED) {
    return "行驶中/车内音频连接";
}
```

问题：**人下车后，车机蓝牙音频还会保持连接一段时间**（甚至一直连着）。  
于是：

- 车辆状态显示“行驶中”；
- 自动上锁被 `evaluateInCarOrDrivingState()` 否决；
- 人已经在车外，App 仍不允许锁车。

### 2. 通知栏“行驶中”没有时效

`lastObservedParkStatus` 一旦被解析成“行驶中”，就永久生效。  
如果通知栏文字没有再次刷新成“已驻车”，会一直挡住锁车。

### 3. BLE 旧“行驶中”快照信任 5 分钟

`0x0121` 的 `snap.timestampMs` 是收到时间；旧逻辑只要 5 分钟内收到过“行驶中”，就一直优先返回 DRIVING，即使后来已经 P 档/已驻车。

---

## 二、v3.14 修复

### 1. 移除 A2DP/HFP 的行驶判定

`resolveEffectiveVehicleParkState()` 和 `evaluateInCarOrDrivingState()` 不再用 A2DP/HFP 判断行驶。

原因：车机音频连接 ≠ 车辆在行驶；P 档、人下车、车机音响还连着是正常场景。

### 2. 通知栏状态加时间戳

`KeyNotificationBridgeService`：

```java
lastObservedParkStatusAtMs
```

- 只有状态**变化**时才更新时间；
- “行驶中”只在 90 秒内有效；
- “已驻车”可在 5 分钟内作为驻车证据。

### 3. BLE/组件“已驻车”优先

- BLE/组件明确 `isParked()`（EPB=1/2 或“已驻车”）→ 先判定 PARKED；
- BLE“行驶中”只在 **30 秒内**可信；
- 真实车速 >1.8 m/s 仍优先判 DRIVING（安全兜底）；
- 通知栏“行驶中”不能覆盖 BLE/组件的“已驻车”。

### 4. 不再用 25 秒 hold 无条件挡锁

`drivingHoldUntilMs` 只在**还有残余速度 >0.5 m/s** 时生效，不再“停车后 25 秒内一律禁锁”。

### 5. 旧 DRIVING 状态兜底

如果当前状态还是 DRIVING，但没有新鲜 BLE/通知证据、车速 ≤0.5 m/s、hold 已过：

```java
return VehicleParkState.PARKED;
```

避免 UI 永远卡在“行驶中”。

### 6. 手动门控同步修正

`evaluateHardDrivingState()` 里的通知栏“行驶中”也加 90 秒时效，避免旧状态挡住手动上锁。

## 四、边界

- 银河没有直接 P 档 CAN 信号；本版依赖 EPB/通知栏/车速推断；
- 如果车机既不更新“已驻车”，GPS 也无速度，App 会按“无新鲜证据 + 低速”兜底 PARKED；
- A2DP 不再作为行驶证据，极端情况下“车在动但无 GPS/无 BLE 状态”可能误判为驻车，但真实车速 >1.8 m/s 仍会拦住；
- 若仍有“ACL 闪断 10 秒熔断”，那是蓝牙防抖，不是行驶误判，最多 10 秒。
