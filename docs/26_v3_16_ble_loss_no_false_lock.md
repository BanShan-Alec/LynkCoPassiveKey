# 26. v3.16：关闭蓝牙/信号丢失不再误触发锁车

## 一、结论先说

你担心的场景：

> 车旁解锁 → 关闭蓝牙 → 信号消失 → 被当成“走远” → 自动上锁

**旧版本大部分情况下不会锁**，因为：

- 手机蓝牙关闭会触发 `ACTION_STATE_CHANGED`，设置 15 秒 `glitchHoldUntilMs`；
- 无新 RSSI 超过 8 秒后 `signalFresh=false`，自动上锁分支会清零倒计时。

但确实存在一个**真实漏洞**：

- 如果最后一条 RSSI 是弱值（例如车内多径 -90），随后车机 ACL 断开/不再广播；
- 旧逻辑的 `signalFresh` 允许 **8 秒**；
- 上锁驻留只需 3.2 秒；
- 在蓝牙关闭事件到达前，或车机单方面断开但手机蓝牙还开着时，可能用**旧弱 RSSI**把倒计时走完，误锁。

v3.16 把这个窗口彻底堵上。

---

## 二、v3.16 的三重保护

### 1. 链路断开立即取消倒计时

以下事件一律：

```java
resetAutoLockDwell();
lockInhibitUntilMs = now + 10~15s;
```

- 手机蓝牙 `TURNING_OFF/OFF` → 15 秒禁用自动上锁；
- 车机 `ACL_DISCONNECTED` → 立即清零 + 10 秒禁用；
- BLE 扫描注册失败 → 清零 + 5 秒禁用；
- 手机蓝牙重新开启 → 8 秒稳定期禁用。

日志：

```text
🛡️ 车机BLE链路断开 -> 立即取消自动上锁倒计时（禁止用旧RSSI误锁）
🛡️ 自动上锁已取消：手机蓝牙已关闭，禁止用旧 RSSI 误锁
```

### 2. 自动上锁只用 3 秒内的新样本

旧逻辑锁车用 8 秒 `signalFresh`；现在自动上锁单独要求：

```java
now - lastSampleTimestamp <= 3000ms
```

超过 3 秒没有新 RSSI，直接取消倒计时：

```text
信号中断 / 链路断开 — 已取消自动上锁，等待新样本
```

### 3. 至少 3 个新样本

新增：

```java
lockZoneSampleCount
lastLockZoneSampleMs
```

- 同一个 RSSI 样本被重复评估，不会重复计数；
- 必须看到 **3 个不同的新样本** 才允许锁车；
- 锁车条件：

```text
蓝牙开启
+ 3 秒内新样本
+ 至少 3 个样本
+ 连续低于上锁阈值满驻留
+ 不在 10/15 秒禁用窗口
```

因此“最后一条 -90 然后蓝牙消失”不会再走完倒计时。

## 三、场景推演

### 场景 A：车旁解锁后关闭手机蓝牙

- 解锁区本身会重置上锁倒计时；
- 蓝牙关闭事件 → 15 秒禁用 + 样本清零；
- 15 秒后仍无新样本 → 3 秒新鲜度检查失败；
- **不会自动上锁**。

### 场景 B：车机蓝牙关闭/车机停止广播，手机蓝牙仍开

- ACL 断开 → 立即清零 + 10 秒禁用；
- 若没有 ACL 事件，仅停止广播 → 3 秒无新样本 → 取消；
- **不会自动上锁**。

### 场景 C：最后一条 RSSI 是弱值 -90

- 旧逻辑可能用这条 -90 继续累计 3.2 秒；
- 新逻辑必须 3 个新样本 + 3 秒内新鲜度；
- 单条旧值无法完成锁车；
- **不会自动上锁**。

### 场景 D：用户真的走远，正常上锁

- 持续收到新广播/GATT RSSI；
- 样本数 ≥3；
- 低于阈值满驻留；
- 正常自动上锁不受影响。

---

## 四、边界

- 关闭蓝牙后，**自动上锁会被禁用**；这是安全取舍：宁可少锁一次，也不能用旧 RSSI 误锁。
- 关闭蓝牙后手动锁车也无法通过蓝牙下发；需要重新开蓝牙或使用车钥匙/车机。
- 自动上锁需要至少 3 个新样本，驻留时间很短（如 0.5s）时实际会稍微延长到约 2 秒（1Hz 样本）。
- 如果 OEM 在息屏时完全停止 BLE 回调，自动上锁会取消，不会误锁。
